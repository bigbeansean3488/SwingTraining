# 棒球隊管理與訓練分析平台：專案任務書

> 這份文件是整個專案的唯一依據。每次開始工作前請先讀完，並讀 `docs/PROGRESS.md` 確認目前進度。
> 文件中的套件名稱與免費額度是 2026 年 11 月的狀況，動手前請查官方文件確認現況，有出入時以官方文件為準並回報。

## 1. 專案目標

為一支大學以上的成棒球隊（球員皆為成年人、僅供隊內使用、不對外販售）開發一個網頁應用程式，整合三件事：

1. **球隊管理**：名單、角色、行事曆、出席。
2. **訓練工具**：訓練紀錄，以及用單支手機影片做骨架追蹤，產出揮棒與投球的動作指標。
3. **比賽記錄**：逐球記錄並自動算出攻守數據。

最終價值是**把每位球員的訓練成果與比賽成果放在同一條時間軸上對照**。

## 2. 不可違反的限制

- **零費用**：只使用免費方案。任何需要付費、綁信用卡、或購買網域的做法，都要先停下來問我，不可自行決定。
- **一支手機就能用**：不需要額外硬體、不需要電腦、不需要安裝原生 App。iOS Safari 與 Android Chrome 都要能用。
- **任何有網路的地方都能連**，沒網路時核心功能（骨架分析、記錄輸入）仍可運作，恢復連線後同步。
- **不使用學校或研究室的伺服器、NAS**。
- **不做逆向工程**：不拆解、不抓取、不模仿 GameChanger、SwingX 或其他商用產品的程式、私有 API、介面與評分公式。只參考公開的棒球記錄規則與運動生物力學文獻。
- **不做的功能**：比賽直播、影片精華剪輯、對外公開的球員頁面、金流。

## 3. 架構

| 層 | 選擇 | 說明 |
|---|---|---|
| 前端 | Vite + React + TypeScript，做成 PWA | 可加入主畫面、可離線 |
| 代管 | Cloudflare Pages | 使用免費的 `*.pages.dev` 網址，不買網域 |
| 骨架分析 | MediaPipe Pose Landmarker 網頁版（`@mediapipe/tasks-vision`） | 完全在手機瀏覽器內運算，影片不上傳 |
| 後端 | Supabase 免費方案 | 登入、Postgres 資料庫、列級權限 |
| 本機儲存 | IndexedDB | 離線暫存、待同步佇列、選擇性保留影片 |
| 備份與保活 | GitHub Actions 排程 | 每天連線一次避免專案被暫停，每週匯出資料庫 |

**資料流**：手機內建相機錄慢動作影片 → 在網頁中選取影片 → 瀏覽器逐幀推論骨架 → 計算指標 → 只把骨架座標（壓縮）、指標、少量關鍵幀截圖同步到 Supabase。

**設計原則**

- 原始影片預設不上傳。Supabase 免費方案檔案空間只有 1 GB、單檔上限 50 MB。
- 分析引擎（`src/analysis/`）是純函式：輸入關鍵點時間序列，輸出事件與指標。不可依賴 React、DOM 或 Supabase，以便單獨測試，日後也能搬到別的環境。
- 比賽資料採事件紀錄：每一球存一筆事件，所有統計值由事件即時計算，不直接儲存統計值。
- 所有資料列都帶 `player_id` 與時間戳，訓練與比賽才能對照。
- 資料庫結構全部用 SQL migration 檔管理，放在版本控制內，日後可搬到其他 Postgres。

## 5. 開發階段

每個階段都要：開分支、小步提交、通過測試與型別檢查、開 Pull Request、更新 `docs/PROGRESS.md`。**一個階段完成並經我在實機上確認後，才開始下一個階段。**

### 階段 0：專案骨架

- 建立 Vite + React + TypeScript 專案、ESLint、Prettier、Vitest。
- 設定 PWA（manifest、service worker）。
- 建立 `CLAUDE.md`、`README.md`、`docs/` 各檔。
- GitHub Actions：每次推送跑 lint、型別檢查、測試、建置。
- 寫出 Cloudflare Pages 的部署步驟（哪些步驟需要我本人在瀏覽器上操作，請逐步列出）。

驗收：我可以用手機打開部署後的網址，看到首頁，並能加入主畫面。

### 階段 1：單機骨架分析（不需要後端，是全專案風險最高的部分）

- 選取影片 → 逐幀骨架推論 → 骨架疊圖播放（可逐幀前後移動、可調播放速度）。
- 打擊分析第一版（側面機位），指標見第 6 節。
- 分析結果頁：關鍵幀截圖、指標數值、各指標的簡短白話說明。
- 拍攝引導頁：機位、距離、高度、光線、幀率設定的圖文說明。
- 結果可匯出 JSON；歷史紀錄暫存在 IndexedDB。
- 顯示實際取得的影片幀率與每幀信心值，低於門檻時提示重拍，不輸出不可靠的數字。

必須驗證並寫進 `docs/DECISIONS.md` 的技術風險：

1. iPhone 與 Android 的慢動作影片從網頁選取後，實際拿到的幀率是多少；如何取得原始高幀率檔。
2. 逐幀擷取的做法（例如 `requestVideoFrameCallback`、WebCodecs、逐步 seek）在 iOS Safari 與 Android Chrome 上哪一種可靠。
3. 不同等級手機處理一支 3 秒、240 fps 影片所需的時間；必要時提供降採樣選項。
4. MediaPipe 模型的 lite、full、heavy 三種版本在手機上的速度與穩定度取捨。

驗收：我用自己的手機拍一支揮棒影片，能在 1 分鐘內看到疊圖與指標；同一支影片重複分析，結果一致。

### 階段 2：帳號與球員檔案

- Supabase 專案設定步驟（列出需要我操作的部分）、登入（Email 魔術連結或 Google，擇一並說明理由）。
- 資料表與列級權限，見第 7 節。
- 球員檔案頁：基本資料、分析歷史、指標趨勢圖。
- 離線佇列：離線時的分析結果先存本機，上線後自動同步，衝突處理規則要寫清楚。
- GitHub Actions：每日保活、每週資料庫備份。備份存放位置請提出免費方案並說明，不可把含個資的備份放進公開儲存庫。

驗收：兩支手機登入不同帳號，球員只看得到自己的資料，教練看得到全隊。

### 階段 3：訓練紀錄與投球分析

- 訓練課表與手動紀錄（打擊數、牛棚球數與球種、體能測驗、自訂項目）。
- 投球分析第一版（側面機位），指標見第 6 節。
- 兩次分析的並排比較（同步在關鍵事件點）。

### 階段 4：球隊管理

- 球隊、球季、名單、角色（管理員、教練、球員）、邀請連結。
- 行事曆（訓練、比賽）與出席回覆。

### 階段 5：比賽記錄

- 先做**簡化模式**：以打席為單位輸入結果（安打種類、出局方式、保送、三振、打點、得分）。
- 再做**逐球模式**：球數、球種、好壞球、擊球落點、跑者推進、守備位置、換人。
- 由事件計算打擊、投球、守備的基本數據，以及落點圖與用球數。
- 可修改或刪除任一筆事件，數據自動重算。
- 棒球記錄規則的例外情況很多（代打、代跑、失誤、自責分、野手選擇等），請先列出要支援的範圍讓我確認，不要一次做完全部。

### 階段 6：整合報表

- 球員時間軸：訓練量、動作指標、比賽數據放在同一張圖上。
- 教練總覽：全隊各指標的分布與個人變化。
- 匯出 CSV。

## 6. 動作指標（第一版）

單支手機、單一視角得到的是 2D 資料，下列指標都是**相對值與趨勢參考，不是實驗室等級的量測**。介面與報告中必須如實說明這一點。每個指標的定義、公式、適用視角與限制要寫進 `docs/METRICS.md`，並附參考文獻；找不到文獻依據的指標標示為「實驗性」。

長度一律用身高（或肩寬、軀幹長）做正規化，不直接顯示像素。訊號在計算速度與角度前要先濾波，濾波方法與參數寫進文件。

**打擊（側面機位，鏡頭垂直於投打連線、面對打者正面）**

- 動作分期與各階段時間：預備、抬腳、前腳著地、擊球、收棒
- 跨步長度
- 重心前移量（以骨盆中心為代理）
- 頭部位移（水平與垂直）
- 前腳著地與擊球瞬間的前膝角度
- 擊球瞬間的軀幹傾斜角
- 手腕最大速度及其發生時間
- 骨盆與肩膀的啟動順序（2D 下只能用代理量估計，標示為實驗性）

**投球（側面機位，鏡頭垂直於投球方向、面對投手正面）**

- 動作分期與各階段時間：抬腿最高點、前腳著地、出手、收尾
- 跨步長度
- 前腳著地與出手瞬間的前膝角度
- 出手瞬間的軀幹前傾角
- 前腳著地瞬間投球手肘相對肩線的高度
- 抬腿最高點到出手的總時間

**明確不做**：棒速、擊球仰角、擊球初速、球速、轉速、甜蜜點。這些需要追蹤球棒或球，單支手機不可靠。

**回饋文字**：第一版用規則式，把指標與球員自己的歷史平均比較，描述「變大、變小、變穩定」，不做「好、壞」的絕對評分，也不給傷害風險或醫療相關判斷。

## 7. 資料模型（起點，可在說明理由後調整）

- `profiles`：使用者基本資料、身高、慣用手
- `teams`、`team_members`（含角色）、`seasons`
- `events`：行事曆項目；`attendance`
- `training_sessions`、`training_logs`
- `motion_analyses`：類型（打擊或投球）、拍攝條件、幀率、模型版本、分析引擎版本、事件時間點、指標（JSON）、壓縮後的關鍵點
- `games`、`lineups`、`game_events`（逐球或逐打席事件）

每筆動作分析都要記錄**模型版本與分析引擎版本**，日後演算法更新時才能判斷數據是否可比較，並能用保存的關鍵點重新計算。

列級權限：球員可讀寫自己的資料；教練與管理員可讀全隊、可寫訓練與比賽資料；非隊員完全無法讀取。

## 8. 免費方案的已知限制

- Supabase 免費方案：資料庫 500 MB、檔案 1 GB、每月流量 5 GB、最多 2 個專案、閒置一週自動暫停、沒有自動備份。
- Cloudflare Pages 免費方案：每月 500 次建置。請避免每次小提交都觸發正式部署。
- Firebase 的檔案儲存需要綁付費帳戶，不採用。
- 在介面的管理頁顯示目前資料庫用量的估計值，接近上限前提醒。

## 9. 工作規則

- 介面文字、文件、提交訊息的說明使用繁體中文（台灣用語）；程式碼的識別字與註解用英文。
- 介面以手機直向為主，按鈕要夠大，戶外強光下可讀。
- 開始每個階段前，先提出該階段的實作計畫與待確認問題，我同意後再動手。
- 需要我本人操作的事（註冊帳號、在網站後台點選、貼上金鑰）請給逐步指示，並告訴我做完後要回報什麼。
- 金鑰與密碼只放在環境變數與 GitHub Secrets，絕不寫進程式碼或提交紀錄。
- 分析引擎的每個指標都要有單元測試，用 `tests/fixtures/` 內的關鍵點資料驗證。
- 不提交真人影片或可辨識個人的資料到儲存庫。
- 沒有實機驗證過的功能，不可在進度文件中標示為完成；請明確區分「已寫完」「已通過自動測試」「已在實機確認」。
- 遇到與本文件衝突、或本文件沒寫到的重大決定，先問我。
- 每次工作結束前更新 `docs/PROGRESS.md`：完成了什麼、怎麼驗證的、已知問題、下一步。
