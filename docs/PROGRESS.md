### 需要使用者做的事（依序）
1. 合併 PR（階段 0～6 是疊在一起的分支，依序合併）。
2. 照 `README.md` 部署到 Cloudflare Pages，手機開啟、加入主畫面（階段 0 驗收）。
3. 用自己的手機拍一支側面揮棒影片分析，回報「分析 → 診斷與效能」的截圖（階段 1 驗收與技術風險 1～4）。
4. 照 `docs/SETUP_SUPABASE.md` 設定 Supabase、Google 登入、GitHub Secrets，做兩支手機的權限驗收（階段 2）。
5. 確認待確認事項：`docs/SCORING_SCOPE.md`（比賽記錄範圍）、`docs/DECISIONS.md` D15（隊友能看到彼此姓名；比賽數據全隊可讀）。
6. 已設定 Supabase 的話，在 SQL Editor 執行 `supabase/migrations/20261117000000_reference_motions.sql`（標竿動作）。之後用教練或學長的示範影片設一個標竿，再用自己的影片按「與標竿對照」，回報骨架是否對得上。

### 已知問題與限制
- iPhone 從主畫面開啟時，Google 登入轉址後能否回到 App 未驗證（D13）。
- iPhone 慢動作影片從「照片」選取時可能被轉成 30 fps（D9 風險 1），App 會偵測並提示，但取得原始檔的方法需要實測。
- HEVC 影片在 iOS Safari 能否用 WebCodecs 解碼未驗證；不能時會改用較慢的逐格跳轉。
- 一場比賽只能有一位記錄員；自責分採簡化規則（見 SCORING_SCOPE）。
- GitHub 公開儲存庫 60 天無活動會停用排程，保活工作已嘗試自動重新啟用，未驗證。
- 打擊的前腳著地比實驗室資料晚約 60 毫秒（OBP 資料驗證，D23）；擊球時間已在 1.2.0 修正（D24），但 60 ms 的校正只在實驗室資料驗證過。
- `npm audit` 有建置工具（workbox-build）的 moderate 警告，不影響使用者端（D8）。

- 使用者回報：打擊的擊球與收棒都抓得太早，擊球時還沒打到。
- 舊的打擊結果（1.1.x）會顯示「用目前引擎重新計算」，重算後才會跟新結果比較。
- 真實影片觀察（桌機 Chrome，Wikimedia Commons 影片，不算實機驗證）：
  - Conforto 揮棒（CC BY-SA 4.0，30 fps，面對打者正面）：新版擊球 2.067 秒，畫面上球棒正好在擊球區；舊版會判在 2.000 秒，那時球棒還在肩膀後方。收棒 2.233 秒，手已收到肩膀附近。
  - 同一支影片的前腳著地自動抓不到（腳落地後還在滑動，速度一直沒降下來），要手動標記；舊版一樣抓不到。影片 3.0～3.5 秒有剪接的淡入淡出，分析範圍不能包含。

    - 廣島 38 號打擊（CC BY-SA 3.0，24 fps，從打者背後拍）：自動分析成功，擊球 2.333 秒與畫面一致（球棒在擊球區，下一格斷棒）；角度不對，長度與角度不能用。
    - Carpenter 打擊（CC BY-SA 4.0）：每格重複 3 次的慢動作，App 正確判為 `timing_implausible`。換算時間比例後，手速最快出現在送棒繞肩時（擊球時手朝鏡頭方向移動，畫面上動得少），擊球判錯，需要手動標記。
    - Pedroia 打擊（CC BY-SA 3.0）：人太小、被前景擋住，追蹤成功 64%，失敗。
    - Maeda 投球（CC BY-SA 3.0，24 fps，面對投手正面）：自動分析成功；抬腿最高點、前腳著地與畫面一致，出手比畫面晚約 20～40 ms（不到一格；投球手在那幾格超出暗角）。實驗室資料反而是早 14 ms，出手暫不修改（D25）。
    - Harrison 投球（CC BY 4.0，高處斜後方）：前腳著地與跨步明顯錯誤，不能用。
