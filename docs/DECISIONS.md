# 技術決定與理由

每筆決定記錄：日期、決定、理由、影響。需要使用者確認的標記 **【待確認】**。

## D1：沿用原儲存庫，舊程式保留在 tag（2026-11-14）
- 決定：在原 `SwingTraining` 儲存庫重建，舊的純 JS 揮棒分析專案保留在 tag `legacy-v0`。
- 理由：保留歷史與 GitHub 設定；舊程式隨時可用 `git checkout legacy-v0` 取回參考。
- 舊專案的經驗（見 `legacy-v0:docs/validation-status.md`）：在桌機 Chrome 上 4K 影片逐步 seek 每幀約 0.9 秒、播放式擷取的關鍵點落後 0.2～0.3 秒。這直接影響 D6。

## D2：TypeScript 用 6.0，不用 7.0（2026-11-14）
- 決定：`typescript@~6.0.3`。
- 理由：npm 上最新是 7.0.2，但 `typescript-eslint@8.72` 的 peer 依賴是 `typescript <6.1`，用 7.0 會讓 ESLint 型別規則失效。等 typescript-eslint 支援 7 再升級。

## D3：雜湊路由（`#/path`）（2026-11-14）
- 決定：自己寫約 40 行的 hash router，不引入 react-router。
- 理由：靜態代管與已安裝的 PWA 都不需要伺服器改寫規則；少一個依賴。

## D4：Cloudflare Pages 用 Git 整合部署，只部署 `main`（2026-11-14）
- 決定：Cloudflare 直接連 GitHub，Preview branch 設為 None。
- 理由：設定最簡單、不需要 API token；只有合併到 `main` 才算一次建置（免費 500 次／月，2026-11 官方文件確認）。CI（lint／測試）在 GitHub Actions 跑，不佔 Cloudflare 建置次數。

## D5：MediaPipe wasm 自行代管，模型從 Google 下載後快取（2026-11-14）
- 決定：`npm install` 時把 `@mediapipe/tasks-vision` 的 wasm 複製到 `public/mediapipe/wasm`，由我們的網域提供；`.task` 模型檔從 `storage.googleapis.com/mediapipe-models` 下載，service worker 用 CacheFirst 快取。
- 理由：wasm 版本與 npm 套件一致，不受 CDN 影響；第一次分析後即可離線分析。不預先快取（約 10～30 MB），避免每個使用者安裝 PWA 時都下載。
- 影響：第一次分析需要網路。離線前請先在有網路時開一次分析頁（App 有「預先下載模型」按鈕）。

## D6：逐幀擷取優先用 WebCodecs，seek 作為備案 【待實機驗證】（2026-11-14）
- 決定：用 `mp4box.js` 解析 MP4/MOV 容器，`VideoDecoder`（WebCodecs）依序解碼每一幀，直接把 `VideoFrame` 送進 MediaPipe。瀏覽器不支援或解碼失敗時，退回「逐步 seek + `requestVideoFrameCallback` 確認畫面已更新」。
- 理由：
  - 舊專案實測 seek 每幀約 0.9 秒（4K），3 秒 240 fps＝720 幀會超過 10 分鐘，達不到 1 分鐘驗收。
  - 播放式（`requestVideoFrameCallback` 邊播邊推論）會跳幀，舊專案在無頭 Chrome 觀察到關鍵點落後，結果不可重現。
  - WebCodecs 依序解碼不需要 seek，每一幀都處理，時間戳直接來自容器（＝真實幀率），同一支影片每次輸入完全相同，結果可重現。
- 支援度（依文件，**未實機驗證**）：Android Chrome 支援 WebCodecs；iOS Safari 16.4 起支援 `VideoDecoder`。HEVC（iPhone 預設）是否能用 `VideoDecoder.isConfigSupported` 解碼要在實機確認。App 的「診斷」頁會顯示實際用了哪種方法。

## D7：Supabase 金鑰
- 決定：前端只用 Supabase 的 publishable（anon）金鑰，透過 Cloudflare Pages 的環境變數 `VITE_SUPABASE_URL`、`VITE_SUPABASE_PUBLISHABLE_KEY` 注入。資料由列級權限（RLS）保護。`service_role`／secret 金鑰只放 GitHub Secrets 給備份用，絕不進前端。

## D8：npm audit 的已知警告（2026-11-14）
- `vite-plugin-pwa@2.0.0` → `workbox-build` 依賴有 moderate 等級警告（deepmerge、glob、minimatch）。只在建置時執行、不進到使用者的瀏覽器，風險可接受。`npm audit fix --force` 會降級到 vite-plugin-pwa 1.1，不採用。

- 所有資料先寫進 IndexedDB，同時記一筆到 outbox；有登入且有網路時才同步（階段 2）。
- 第一次開啟自動建立「我」這個球員檔案，所以不用註冊就能分析。登入後這個檔案會連結到帳號。

## D11：關鍵點儲存格式（2026-11-14）
- 只存 19 個用得到的關鍵點；座標量化成 16 位元（範圍 −0.25～1.25，精度約 0.04 像素 @1920）、visibility 8 位元，與前一幀做差分後 gzip，再轉 base64 存成文字欄位。
- 實測：126 幀約 14 KB，3 秒 240 fps（720 幀）約 80 KB。Supabase 500 MB 約可存 5,000 筆以上的分析。
- 有版本號（`KP` v1），可以用保存的關鍵點以新版引擎重算。

## D12：React 編譯器相關的 lint 規則關閉（2026-11-14）
- `eslint-plugin-react-hooks@7` 的 `set-state-in-effect`、`refs`、`use-memo` 是給 React Compiler 用的嚴格規則，會把常見且正確的 effect 寫法標成錯誤。本專案沒有使用 React Compiler，因此關閉這三條，其餘 hooks 規則保留。

## D13：登入方式選 Google，不選 Email 魔術連結（2026-11-14）
- 決定：Supabase Auth 的 Google provider。
- 理由：
  - Supabase 官方文件：自 2024-09-26 起，沒有自訂 SMTP 的專案只能寄信給專案組織成員，且全專案每小時約 2 封；魔術連結必須另外申請寄信服務（SMTP），多一個帳號與額度要管理。
  - 成大的學校帳號就是 Google Workspace，隊員都有 Google 帳號；Google Cloud 建立 OAuth 用戶端免費、不需帳單。
- 風險【待實機驗證】：iPhone 從主畫面開啟的 PWA 在 OAuth 轉址後能否回到 App 並保留登入。若不行，改用 Safari 版使用，或之後加上 Email 驗證碼（需要 SMTP）。

## D14：離線佇列與衝突處理規則（2026-11-14）
- 每筆資料用手機產生的 UUID，離線也能建立；每次修改都記到 outbox。
- **上傳**：依資料表相依順序（球員檔案 → 球隊 → 成員 → …）以 id upsert。
- **衝突規則：最後修改者勝（last write wins），以整列為單位。** 比較的是手機上的修改時間 `updated_at`；伺服器端觸發器拒絕較舊的修改，下載時手機也保留較新的本機版本。兩支手機同時改同一筆不同欄位時，較晚修改的整列覆蓋較早的。
- **刪除**用墓碑（`deleted_at`）同步，刪除也遵守最後修改者勝。
- **下載**：每張表記一個游標（伺服器寫入時間 `server_updated_at`），只抓之後變動的列；RLS 自動過濾成自己有權限的資料。
- 伺服器拒絕（權限不足、資料不合法）的變更不會無限重試：從佇列移除、留在本機，並在「帳號與同步」頁列出。網路錯誤則保留，稍後重試。
- 比賽記錄假設**同一場比賽只有一位記錄員**；兩人同時記錄同一場會互相覆蓋（列為已知限制）。
- 依賴手機時鐘：手機通常自動對時，誤差在秒級，對「最後修改者勝」影響可忽略。

## D16：備份存放位置（2026-11-14）
- 每週 `pg_dump`（public schema）＋帳號對照表，以 AES-256 加密後存成 GitHub Actions artifact（保留 90 天）；可選擇同時推到私有儲存庫保留半年。
- 公開儲存庫的 artifact 可能被其他 GitHub 使用者下載，所以只存加密檔；密碼只在 GitHub Secrets 與管理員的密碼管理器。
- 不採用：Cloudflare R2（需綁付款方式）、Google Drive（需服務帳號與額外設定）、直接存進公開儲存庫（違反任務書）。
- 每日保活呼叫資料庫函式 `ping()`；同時透過 GitHub API 重新啟用排程工作，避免公開儲存庫 60 天無活動被停用（未驗證）。

## D18：非實地影片的觀察紀錄（不算實機驗證）（2026-11-14）
- 測試影片：舊專案留下的 iPhone 4K 直式影片（31.6 fps、室內投球機台、非側面機位、手持），不進版本控制。
- 打擊分析：正確拒絕（影片內是投球，不是揮棒）。
- 投球分析：拒絕（`events_not_found`）。原因：31.6 fps 下偵測到的出手時刻，前腳踝速度仍為 3.0 軀幹長/秒（高於門檻），出手前找不到「前腳著地」。在低幀率、非側面機位下拒絕是預期行為，**沒有為了讓這支影片通過而調整門檻**。
- 這支影片的追蹤成功率 100%、平均信心值 0.84。

## D21：影片讀取逾時與跨步負值（分析引擎 1.1.0）（2026-11-16）
- 背景：使用者實測回報兩個問題：選影片時常出現 time out；跨步長度出現負值。
- 讀取逾時：
  - 原因（推測，未在實機確認）：選影片後要等瀏覽器載入第一個畫面（`loadeddata`），15 秒沒等到就失敗。iOS Safari 對沒在播放的影片常常不載入畫面，大檔案也容易超過 15 秒。逐格跳轉時只要一格超過 8 秒，整個分析就失敗。
  - 決定：讀到長度與尺寸（`loadedmetadata`）就繼續；等待改為「60 秒沒有讀取進度」才放棄。逐格跳轉超時先重試一次（15 秒），再失敗就跳過那一格；跳過超過 5%（至少 3 格）才算失敗。錯誤訊息改成中文並附建議；失敗的步驟與檔案資訊記在「診斷」頁。
- 跨步負值：
  - 原因：前腳用整段影片判斷，投手出手後後腳往前甩被誤認成前腳；MediaPipe 在側面視角常把左右腳標反。
  - 決定：見 `docs/METRICS.md` §1.5。量出明顯往後跨（小於 −0.1 軀幹長）時不給數字並說明原因，不把錯誤數字當成結果；介於 −0.1 與 0 之間視為「幾乎沒有跨步」記為 0。
  - 舊版（1.0.x）存下的負跨步不列入比較；結果頁的「用目前引擎重新計算」可以更新。
- 驗證：合成資料重現兩種失敗情況（後腳甩過前腳、左右腳標籤在動作中對調），修正後跨步與前膝角度回到正確值（`src/analysis/legs.test.ts`）。還沒用真實影片確認。
- 觀察（不算驗證）：D18 那支非側面的舊投球影片，在 1.0.0 被拒絕（`events_not_found`），1.1.0 找得到事件；桌機 Chrome 強制逐格跳轉跑完 190 幀，跨步量測圖畫在正確的兩隻腳上。那支影片不是側面機位，數值不能拿來判斷準確度。

## D23：研究樣本的 PR 值與參考範圍（修改任務書 §2 回饋規則）（2026-11-17）
- 背景：使用者回饋希望指標有 PR 值，並知道落在什麼區間，例如職業與業餘選手的比較。
- 決定（使用者 2026-11-17 同意修改「只跟自己比較、不做好壞評分」的限制，並選擇中性措辭）：
  - 每個指標顯示「研究樣本 PR」：在公開研究樣本中，大約有多少比例的人數值比這次小。
  - 只用中性措辭：「常見範圍」（中間 50%）、「比常見範圍大／小一些」、「少見」（10%～90% 以外）。不使用「良好／差勁／待加強」。
  - 只有在樣本中與球速或擊球初速有統計關聯的指標（Benjamini–Hochberg 偽發現率 5%），才另外標出「較快的三分之一」常落的範圍，並註明有關聯不代表因果。不顯示球速或擊球初速的數字。
  - 投球另外顯示小聯盟加獨立聯盟（職業組，18 人）的中間範圍。其他分組人數不足 15 人就不顯示。
  - 仍然不做傷害風險或醫療判斷。
- 資料：The OpenBiomechanics Project（Driveline，CC BY-NC-SA 4.0）。用 App 自己的引擎、投影成正側面後計算，方法、驗證與限制見 `docs/REFERENCE_DATA.md`。App 內附出處、授權連結與「不是個人建議」的說明。
- 不採用：
  - 直接引用文獻的 3D 數值：量法不同，不能跟手機 2D 數字比較。
  - 職業比賽轉播或 YouTube 影片：沒有授權，條款不允許下載。
- 公開授權影片（Wikimedia Commons，CC0／CC BY／CC BY-SA）只用來測試分析流程，以及當作標竿動作的範例（D22），不用來計算範圍；原始影片不提交。
- 驗證時發現：打擊的「擊球」自動偵測比實驗室事件早約 60 毫秒（用手腕速度峰值代替擊球瞬間）。研究樣本也是用同一套自動偵測算的，所以 PR 值可以比；修正事件定義需要另外決定，因為會改變指標，要調高引擎版本。

## D24：打擊擊球與收棒時間修正（分析引擎 1.2.0）（2026-11-17）
- 背景：使用者回報打擊骨架分析的「擊球」和「收棒」都抓得太早，擊球時球還沒打到。D23 用 OBP 實驗室資料驗證時也看到擊球平均早 61 ms。
- 原因：
  - 擊球：1.1.0 用手腕速度峰值代替擊球。實驗室資料顯示手在擊球前約 60 ms 就達到最快，之後減速、把速度傳給球棒。
  - 收棒：1.1.0 用「手速降到峰值 25%」。擊球後手速會先短暫降低（約擊球後 40 ms），再在送棒時加速，舊規則停在這個低點。
- 決定：
  - 擊球＝手速峰值 + 60 ms（OBP 中位數 61 ms，四捨五入；固定的時間差，不隨影格率改變）。超出影片時不給擊球時間，並提示把結束時間往後調。
  - 收棒＝擊球後的手速低點之後，找送棒的手速高峰，再找手速第一次降到揮棒峰值 20% 以下的時刻。
  - 前腳著地搜尋到擊球為止（原本到手速峰值，也就是舊的擊球）。METRICS 原本就定義「擊球前」，擊球移後要跟著移；OBP 自動分析成功率 659/677 → 675/677。前腳著地的偏差（+62 ms）沒有更好的簡單規則（比較過速度比例、水平位移比例、腳踝高度回到地面，誤差範圍都約 140 ms），暫不修正。
  - 用 OBP 比較過的其他候選：手速降到峰值某個比例、手往投手方向的位置或速度、前手肘伸直，誤差都比「峰值 + 60 ms」大（`scripts/obp/eval-contact.mjs`）。
- 影響：前腳著地→擊球、擊球→收棒、擊球瞬間的前膝角度、軀幹傾斜、重心前移、頭部位移都改在新的擊球時間量。研究樣本範圍已用 1.2.0 重新產生。
- 版本比較：新增 `src/analysis/versions.ts`，記錄每類動作在哪個引擎版本改過定義（打擊 1.0.0、1.1.0、1.2.0；投球 1.0.0、1.1.0）。個人歷史比較、「好的動作」對照、研究樣本都只跟同一套定義的結果比較；標竿動作對照（D22）遇到不同定義時顯示提醒：1.1.x 的打擊結果不再和 1.2.0 比較（可在結果頁按「用目前引擎重新計算」更新），投球照常比較。原本只看主版本，1.0.x 與 1.1.x 會互相比較，現在也分開。
- 限制：60 ms 來自美國大學為主的實驗室打者（揮擊有球的打擊練習），沒有在真實手機影片上驗證；打擊「前腳著地」仍比實驗室晚約 60 ms（未修正，見 `docs/REFERENCE_DATA.md` §3）。

## D25：投球出手時間暫不修改（2026-11-18）
- 背景：Commons 投球影片（Maeda、Ryu）看起來出手判得偏晚，使用者同意檢查校正。
- 查到的結果：
  - OBP 實驗室資料（206 球，模擬 24～240 fps 加雜訊）：手腕速度峰值比真正出手早 14 ms，不是晚；90% 誤差 18～32 ms（`scripts/obp/eval-release.mjs`）。
  - 「峰值內插到格與格之間 + 12 ms」可把平均誤差降到 0～2 ms、90% 誤差 6～13 ms，但會讓出手平均往後移。
  - 重新核對 Maeda 影片：實際只晚 20～40 ms，不到一格（24 fps），且投球手在那幾格超出望遠鏡暗角、手腕追蹤卡住。
- 決定（使用者 2026-11-18）：先不改，等手機以 120／240 fps 正側面拍攝的投球影片確認後再決定。真實影片判晚主要來自影格間隔與動作模糊，固定時間差修不好。

## D26：擊球那一格往後取整、分析時間改記分析當下（分析引擎 1.3.0）（2026-11-18）
- 背景：使用者回報兩個問題：(1) 打擊擊球的關鍵幀有時還沒打到球；(2) 網頁記錄的分析時間跟現實時間不一樣。
- 擊球那一格：
  - 原因：1.2.0 的擊球估計平均誤差約 0，但取「最接近」的一格，誤差前後各半，所以約一半的揮棒會顯示擊球前一格（OBP：30 fps 44%、120 fps 69%）。
  - 決定：手速峰值用拋物線內插到格與格之間、加延遲，取當下或之後的第一格。延遲依影格率調整（使用者提議）：69 ms − 0.15 × 每格時間（最多減 7 ms）。固定 65 ms 時 240 fps 仍有 21% 落在擊球前（App 建議的拍法反而最差），調整後各影格率都在 5～11%；擊球時間平均晚 8～15 ms（`scripts/obp/eval-contact.mjs`）。
  - 打擊定義改變：`versions.ts` 打擊新增 1.3.0；1.2.x 的打擊結果不與 1.3.0 比較（可按「用目前引擎重新計算」）。投球不變。研究樣本用 1.3.0 重新產生。
- 分析時間：
  - 原因：`recorded_at` 原本取影片檔案的修改時間（`File.lastModified`）。手機回報的檔案時間可能是拍攝、匯出或複製的時間，不是分析時間。
  - 決定（使用者要求兩個時間都標示）：
    - 拍攝時間：從影片檔的影片資訊（MP4/MOV 的 moov/mvhd 建立時間）讀取，存在 `capture.filmedAt`。讀不到時退回手機的檔案時間並註明「可能不準」（`capture.fileLastModified`）；兩者都沒有就顯示「不明」。2005 年以前、零或未來的時間視為無效。
    - 分析時間：`created_at`。
    - `recorded_at`（排序與趨勢圖用）＝拍攝時間（影片資訊），沒有就用分析時間。
    - 結果頁兩個時間都顯示；分析列表顯示分析時間，讀得到影片資訊時也顯示拍攝時間。
  - 影響：舊的分析 `recorded_at` 仍是檔案時間，結果頁會標成「手機的檔案時間，可能不準」。影片資訊的讀取只用合成檔案測過，iPhone／Android 實際影片是否都有記錄、iOS 選取影片時是否保留，需要實機確認。

## D27：對外的單獨分析版（2026-11-18）
- 背景：使用者想把骨架分析單獨拿出來，給球隊以外的人使用。任務書 §1 寫「僅供隊內使用」，這是範圍變更。
- 決定（使用者 2026-11-18 選擇做法 B）：同一個儲存庫多一個建置版本，另外部署成第二個 Cloudflare Pages 專案（免費 `*.pages.dev`）。
  - `npm run build:solo`（`vite --mode solo`）：入口 `src/SoloApp.tsx`，只有打擊／投球分析、結果、並排比較、拍攝引導、指標說明、診斷，以及「更多」頁（名字、備份、資料說明、授權、清除資料）。
  - 不連 Supabase：不登入、不同步。建置時把 Supabase 環境變數清空，打包結果不含 Supabase 程式（已檢查 `dist/assets`）。`saveRow` 不寫同步佇列。本機資料庫名稱跟球隊版分開（`motion-analysis`）。
  - 不含標竿動作（球隊功能，且可能來自別人的影片）；可以用「標記為好的動作」跟自己比較。
  - 備份檔（`src/lib/backup.ts`）：分析、所屬的人、關鍵幀截圖，不含原始影片。匯入時可選「這是我自己的備份」（併入這支手機的「我」，換手機用）或當成另一個人分開保存。同一筆資料以較新的版本為準。
  - 兩個版本共用分析引擎與頁面；版本差異集中在 `SOLO`（`src/lib/edition.ts`）。CI 與 `npm run check` 兩個版本都建置。
- 為什麼不選其他做法：直接給現在的網址（A）會看到用不到的球隊功能；把引擎拆成獨立套件、兩個專案（C）維護成本高，現在不需要。
- 仍要遵守：不做評分、傷害或醫療判斷；回饋只跟自己比較；沒有對外公開的球員頁面（資料不離開使用者的手機）。
- 授權：研究樣本來自 OBP（CC BY-NC-SA 4.0），單獨版「更多」頁附出處，並註明只可非商業使用、職業運動組織或金融分析公司的員工、約聘人員或大股東不得使用。
- 隱私說明：MediaPipe（tasks-vision 1.2.3）會每 60 秒把執行統計（辨識種類、執行模式、處理速度）POST 到 `odml.pa.googleapis.com/v1/log`，程式碼中沒有關閉選項；依程式碼看不含影像。球隊版同樣有這個行為。單獨版已擋掉，見 D28。
- 限制：資料只在使用者的瀏覽器，清除資料或 iPhone 長期未開啟可能遺失；靠使用者自己匯出備份。

## D28：單獨版擋掉 MediaPipe 執行統計（2026-11-18）
- 背景：見 D27 隱私說明。單獨版要給球隊以外的人用，使用者 2026-11-18 決定擋掉。
- 做法：單獨版的 `index.html` 加上 `Content-Security-Policy` meta（`vite.config.ts` 的 `SOLO_CSP`），只限制連線：`connect-src 'self' https://storage.googleapis.com blob: data:`。程式、圖片、樣式不受限制。
  - 允許的是自己的網站（程式、wasm 執行檔）與 Google 的模型下載位置（`.task` 模型檔）；`odml.pa.googleapis.com` 不在名單內，瀏覽器直接拒絕連線。
  - MediaPipe 的統計模組送出失敗後會停止計時器、不再重試（tasks-vision 1.2.3 `vision_bundle.mjs`），所以每次載入辨識器最多在主控台留一行錯誤，不影響分析。
  - 用 meta 而不是 Cloudflare `_headers`：兩個版本共用 `public/`，meta 只會出現在單獨版的建置裡，`npm run dev:solo` 也能測到。
- 不改程式庫本身、不攔截 `fetch`，以後升級 MediaPipe 也不用跟著改。
- 球隊版不變（隊內使用，維持 D5 的做法）。如果之後要新增別的連線（例如其他模型位置），要一起改 `SOLO_CSP`。
- 桌機確認（2026-11-18，`npm run dev:solo`，Chrome）：分析 Conforto 測試片正常完成；主控台顯示 CSP 擋下 `odml.pa.googleapis.com/v1/log`，網路紀錄沒有這個請求；從頁面下載 lite 模型仍成功（200，5.7 MB）。
