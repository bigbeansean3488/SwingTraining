# 實地驗證套件（Field Validation Package）

> English: [field-validation.md](field-validation.md) · 英文版：[field-validation.md](field-validation.md)。兩份內容相同；若有出入，以英文版為準並請同步修正。

V0 目前所有功能**最多只到 `UNIT_VALIDATED`**（用合成資料驗證過）。本文件說明要拍什麼樣的真實影片、怎麼評估，讓拿到影片的當天就能開始實地驗證。

**在完成本文件的評估之前，不新增任何分析功能**（球棒/球追蹤、擊球聲音分析、自動判斷擊球品質、AI 教練、後端、雲端資料庫等）。

---

## 1. 要拍的影片

### 1.1 練習項目

- **打 tee 或空揮**（不需要真人投球）。
- 每一段錄影只拍一位球員。可以的話，用同樣流程拍 2–3 位球員。

### 1.2 鏡頭架設

| 項目 | 要求 |
|---|---|
| 裝置 | iPhone 後鏡頭主鏡頭（1×），不要變焦 |
| 固定方式 | **一定要用腳架**，不可手持；每次揮棒之間不要碰手機 |
| 拍攝角度 | 從打者**胸口那一側（開放側）**拍側面，大致與投手—捕手連線垂直 |
| 高度 | 大約腰部（髖部）高度 |
| 距離 | 全身（含雙腳）、收棒時的雙手、整個跨步都要完整在畫面內並留邊。先從約 5–7 公尺開始，並記下實際距離 |
| 方向 | 建議**橫拍**（跨步比較有空間），並記錄是橫拍或直拍 |
| 格式 | 如果可以，用 **1080p / 60 fps**（設定 → 相機 → 錄影）；若用了 4K/30 或慢動作 120/240 fps 也要記下來 |
| 片長 | **一組揮棒錄成一支影片**（例如連續打 10 球，每球間隔 4 秒以上；App 會自動找出每一棒）。第一棒前至少 2 秒就開始錄。另外也拍幾支**單棒短片**（10 秒內，揮棒前至少 1 秒開始錄），用來比較兩種方式 |
| 背景 | 避免有人在打者後方走動 |

### 1.3 揮棒內容

| 組別 | 數量 | 給球員的指示 |
|---|---|---|
| 正常揮棒 | **20–30 支** | 正常揮棒，每次姿勢、站位一致 |
| 步幅加長 | 2–3 支 | 刻意明顯跨大步 |
| 步幅縮短 | 2–3 支 | 幾乎不跨步 / 很小的步幅 |
| 頭部晃動 | 2–3 支 | 讓頭明顯往投手方向移動或往下掉 |
| 時機改變 | 1–3 支（安全才做） | 刻意明顯晚啟動，或中途停頓一下 |

刻意改變的揮棒總共約 5–10 支。請把它們**穿插在正常揮棒之間**拍（例如在第 10、15、20 支正常揮棒之後），不要全部集中在最後。這樣每支刻意改變的揮棒，拿來比較的基準才會是正常揮棒。

### 1.4 拍攝條件

- **夜間球場燈光下**（主要目標情境）— 必拍。
- 白天 — 如果有機會，用同樣流程再拍一組來對照。
- 選拍：故意拍一支品質很差的影片（太遠、手持、部分身體出畫面），確認 QC 會把它擋下來。

### 1.5 要記錄的資訊（每支影片一列）

用 `tools/field/manifest.example.csv` 當範本：

```
file,condition,start,end,lighting,distance_m,note,expected_swings
```

欄位說明：

| 欄位 | 內容 |
|---|---|
| file | 影片檔名（相對於 manifest 所在資料夾） |
| condition | `normal`（正常）、`longStride`（步幅加長）、`shortStride`（步幅縮短）、`head`（頭部晃動）、`timing`（時機改變）、`other`（其他） |
| start, end | 選填。填了就只分析這段秒數（當成一棒，記得包含揮棒前約 1 秒）；超過 10 秒且沒填，就當成一段練習影片，自動找出每一棒 |
| lighting | 光線，例如 `night-field`、`day` |
| distance_m | 鏡頭與打者距離（公尺） |
| note | 備註（例如有空揮、走出打擊區） |
| expected_swings | 這段影片實際揮了幾棒（用來檢查自動切棒）。步幅、頭部等刻意改變的揮棒請另外錄成獨立影片，因為 condition 會套用到同一支影片的每一棒 |

每個拍攝場次另外記一次（寫在 note 或另一個文字檔）：

- 手機型號與 iOS 版本
- 解析度與設定的 fps
- 白天 / 夜間，以及光線描述（例如「只開內野燈，打者在陰影中」）
- 鏡頭距離（公尺）、高度、橫拍或直拍
- 球員打擊方向（右打 R / 左打 L）
- 練習項目（tee / 空揮）
- 打 tee 時，每一球當下判斷的擊球品質（好 / 中 / 差），如果有的話

## 2. 評估怎麼跑

1. 把影片和填好的 manifest 複製到 `data/local-videos/<場次名稱>/`（此資料夾已被 git 忽略；**影片永遠不要 commit**）。
2. 執行：
   ```sh
   node tools/evaluate-field.mjs data/local-videos/<場次名稱>/manifest.csv out/<場次名稱> full
   ```
   程式會用 headless Chrome 跑真正的 app，依照 manifest 的順序把所有影片當成同一個練習 session 處理，並輸出 `results.csv`、`swings.json`、`summary.txt`。
3. 另外在 **iPhone 本機**（Safari，透過電腦或 GitHub Pages 開啟）處理 5–10 支影片，記錄每支的處理時間和任何失敗情況。
4. 挑幾支揮棒用肉眼檢查骨架疊圖：
   `node tools/check-pose.mjs <影片> 0 <片長> full <輸出資料夾> 12`

## 3. 要檢查的項目（結果記錄在 `validation-plan.md`）

| # | 問題 | 證據 | 通過標準 |
|---|---|---|---|
| F1 | 夜間球場燈光下，骨架追蹤是否可用？ | QC 等級、疊圖截圖 | 夜間正常揮棒中 ≥ 80% 的 QC 為 good / fair |
| F2 | QC 是否對快速揮動的手太嚴格？（已知風險：手臂快速移動時手腕 visibility 會下降） | `qcReasons` 中與手腕相關的原因、被拒絕揮棒的疊圖 | 若被拒絕的揮棒中手腕位置其實是對的，就要**依據這些證據**修正 QC 的手腕門檻 |
| F3 | QC 能否擋下真的很差的影片？ | 刻意拍壞的影片 | 被拒絕，且原因合理 |
| F4 | 事件時間點是否合理？ | 對幾支揮棒跑 `tools/plot-analysis.mjs`，並和逐格看影片比較 | 動作開始 / 踏腳 / 手速峰值 / 結束，與人工標記相差約 2 幀以內 |
| F5 | 正常揮棒之間是否一致？ | 頭部、步幅、時序的分布；正常揮棒的一致性分數 | 正常揮棒的偏差大多 < 2 |
| F6 | 刻意改變是否在對的指標被偵測到？ | `summary.txt` | 步幅加長 / 縮短 → 步幅偏差高於所有正常揮棒；頭部晃動 → 頭部偏差高於所有正常揮棒 |
| F7 | 校準一致性分數的尺度 | 正常揮棒之間絕對差異的分布 | 依資料設定 half-score 值（metric-definitions §6），重跑並記錄 |
| F8 | iPhone 上的實際速度 | 計時紀錄 | 約 5 秒的影片能在練習可接受的時間內完成（目標 < 約 30 秒，記錄實際數值） |
| F9 | 頭部指標用哪個版本 | 頭部晃動組中 head（相對骨盆）與 headAnchored（固定原點）的比較 | 決定哪一個當主要數值，並記錄理由 |
| F10 | 一段影片中的每一棒都有被找到嗎？ | `summary.txt` 的 segmentation 行（找到幾棒 vs `expected_swings`），對照影片 | 每一次真正的揮棒都被找到；誤判（空揮、走動、撿球）列出並記錄；記錄 iPhone 上掃描整段影片的時間 |

只有在 F1–F6 都通過後，`validation-status.md` 中的項目才可以改成 `FIELD_VALIDATED`。失敗就照實記錄，**不要為了讓 demo 好看去調整指標**。
